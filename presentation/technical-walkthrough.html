01 — Architecture

CDM as an external semantic source

Resolved once into a vendor-independent Canonical Model, then projected two ways — a relational projection for deterministic access, a semantic projection for retrieval over free text. The AI layer sits above this data architecture, called only where semantic interpretation genuinely adds value.

CDM source→ Resolver + Validation→ Canonical Model
Structured projection

SQLite. Attributes, single-hop & bounded 2-hop relationships. Deterministic, no model call.

Semantic projection

ChromaDB. Open-ended questions, one embedding per entity. Model called only here.

Structured Semantic → Query Pipeline→ LLM (semantic path only)
WHY

An LLM invoked for every question can't guarantee it never touches parts of the model it wasn't given — routing deterministic questions around it entirely removes that surface.

WHY

Two retrieval shapes exist because two question shapes exist: "what are X's attributes" is a lookup; "what covers a customer's financial holdings" is a search.

02 — Embedding strategy

One chunk per entity, embedded locally, grounded twice

CHUNK

One chunk per entity — name + description + full attribute list + relationship list. Not per-attribute: questions arrive entity-scoped, so retrieval should be too.

MODEL

sentence-transformers / all-MiniLM-L6-v2, local, CPU-only. No API key, no per-query embedding cost, works offline.

STORE

ChromaDB, embedded and in-process — no database server, same reasoning already applied to the structured index.

GUARD

Grounded twice: a pre-generation similarity cutoff decides if there's evidence at all; a post-generation citation check confirms the model's claims actually appear in what it was given.

03 — Data relationships

Same name, two different entities — and the 2-hop path the brief itself needed

FOUND

A real collision in the source data: banking:Account (1 attribute) and crmCommon:Account (7 attributes, 4 relationships) — same bare name, genuinely different entities.

FIX

Namespace-qualified canonical names. No silent merge, no coin-flip — the system asks, using its own real vocabulary:

> What are the attributes of Contact? That name is ambiguous in the ingested CDM scope — did you mean banking:Contact or crmCommon:Contact?
BOUND

Traversal is a plain adjacency-dict BFS, capped at depth 2. No graph database, no unbounded walk.

The brief's own example question, answered for real — 2 hops, not 1:

crmCommon:Contact→ preferredEquipment → crmCommon:FacilityEquipment→ organization → crmCommon:Organization
ZERO-HALLUC.

Structured and traversal hits are template-rendered. The model is never called on this path — there is nothing generated, so there is nothing to hallucinate.

HONEST

Per-entity resolution: one bad reference is skipped and logged, not a failed ingestion run. Unresolved references are surfaced, not dropped silently.

04 — Evidence

Measured, not asserted

Each stage — entity matching, structured retrieval, traversal, vector recall, grounding, refusal — is scored independently against a 27-question evaluation set, so a bad answer is traceable to one stage, not a shrug.

reeeliance's own framing is "AI Readiness" — moving from heterogeneous data to standardized, semantic models. That readiness has to exist before the model is ever called — a schema resolved cleanly, relationships bounded and correct, retrieval measured stage by stage. The model is the last step, not the foundation.
